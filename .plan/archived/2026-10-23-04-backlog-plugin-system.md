# PBI: 外部プラグインによるターゲット拡張

## ユーザーストーリー
コントリビューターとして、本体を太らせずに `sasurahime-*` バイナリで新ターゲットを追加したい、なぜなら50→100ターゲット時代に `GenericCleaner` への直書きではレビューと保守が追いつかないから

## ビジネス価値
拡張性の天井を外す。本体は計測・表示・安全基盤に専念でき、ニッチなツール対応は外部に開放できる。

## 優先度
- 順位: 04 / 4（新規分のみ）
- RICEスコア: 30（Reach=100 / Impact=3 / Confidence=50% / Effort=5.0人週）
- 根拠: エコシステム成熟後の価値で現時点では最後。03とも独立だが、本体安定化（分割・契約強化）の後が望ましい。

## BDD受け入れシナリオ
Scenario: プラグインがscanに並ぶ
  Given `sasurahime-foo` がPATHにある
  When `scan` を実行する
  Then `foo` 行が他のターゲットと同様に表示され、合計に含まれる

Scenario: プラグイン失敗は隔離される
  Given 1つのプラグインが異常終了する
  When `scan` を実行する
  Then 全体は中断せず当該行が `unavailable` になり、他は正常表示される

## 受け入れ基準
- [ ] `sasurahime-*` の発見・実行プロトコル（scan/clean/dry-run）が定義される
- [ ] プラグインのタイムアウト・失敗隔離がある
- [ ] `targets` にプラグイン由来が区別して表示される
- [ ] 本体の `GenericCleaner` 新規追加フロー（HOWTO-ADD-target.md）がプラグイン優先に更新される

## テスト戦略
- E2E: 偽プラグイン（正常・異常終了・タイムアウト）をPATHに置いての検証
- 統合: プロトコル準拠・タイムアウト隔離のテスト
- 単体: プラグイン発見・引数組み立てのテスト

## 見積もり
13 SP（要チームでの見積もり）

## 実装アプローチ
1. 最小プロトコル（`scan --json` 互換出力＋終了コード規約）から始める
2. `CommandRunner` の延長で実装し、失敗は `Unavailable` に写像する
3. サンプルプラグインを1つ同梱する

## 技術的考慮事項
- ABI/プロトコルの安定化が先行条件。拙速な拡張は互換性負債になる
- セキュリティ：任意バイナリ実行のためPATH信頼・署名の扱いを文書化する
