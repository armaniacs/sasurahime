# PBI: グローバル状態の排除と履歴の安全化

## ユーザーストーリー
コントリビューターとして、テストが直列ロックなしで並列に回ってほしい、なぜなら `TEST_LOCK` 待ちとグローバル切替の漏れが開発速度を落とすから

## ビジネス価値
開発リードタイム短縮と削除安全性の構造的向上。利用者への直接価値は薄いが、中断・並列時の欠落事故を減らす。

## 優先度
- 順位: 07 / 7
- RICEスコア: 107（Reach=100 / Impact=2 / Confidence=80% / Effort=1.5人週）
- 根拠: 開発者向けでReachが小さいため最後。ただし他PBIと競合しないため合間に着手可。

## BDD受け入れシナリオ
Scenario: グローバルなしで削除モードが決まる
  Given Trashモードと永続モードの2つの実行がある
  When 並列にテストを実行する
  Then 相互にモードが漏れず両方パスする

Scenario: 中断しても履歴が壊れない
  Given 削除途中で中断した履歴ファイルがある
  When 次回 `stats` を見る
  Then ファイルが壊れず、中断分は二重計上されない

## 受け入れ基準
- [ ] `TRASH_MODE/VERBOSE/DRY_RUN` が引数（`DeleteCtx` 等）で運ばれグローバル参照が削除経路から消える
- [ ] `TEST_LOCK` 直列化が必要なテストが消えるか最小化される
- [ ] `history.json` 追記が排他・fsync付きになり壊れない
- [ ] 外部挙動（CLIフラグ・表示）が不変

## テスト戦略
- E2E: 並列実行でのモード漏れ再現テスト
- 統合: 履歴の同時追記・中断復旧テスト
- 単体: `DeleteCtx` 分岐・履歴トリム（上限1000）のテスト

## 見積もり
3 SP（要チームでの見積もり）

## 実装アプローチ
1. `trash.rs:6-24` に `DeleteCtx` 導入し既存関数は互換ラッパー化
2. `context.rs:8-12` のグローバルを呼び出し点に下ろす
3. `history.rs:8-22` の追記をファイルロック+fsync化

## 技術的考慮事項
- リファクタ定義遵守：振る舞いを変えない。`panic=abort` 下での中断安全性に注意
- `is_skippable_error` の文字列マッチ改善は本PBIに含めず別途
